# Быстрый старт: от голого VPS до работающей инфраструктуры

## Требования к VPS

| Что | Минимум | Комментарий |
|---|---|---|
| ОС | Ubuntu 22.04 / 24.04 или Debian 12 | RHEL-семейство — best-effort, apt-путь оттестирован |
| vCPU | 8 (для `two-vps-split-b` — 4) | зависит от профиля |
| RAM | 16 GB для `core-16`, 32 GB для `all-in-one-32` | 8 GB не поддерживается, см. [`02-profiles.md`](02-profiles.md) |
| Диск | 350 GB SSD для `core-16` | считается с запасом 15 % |
| Swap | выключен | защита от OOM — cgroup-слайсы и `systemd-oomd`, а не своп |
| Доступ | root по SSH | плюс **обязательно** запасной путь: консоль провайдера или один whitelisted IP |
| Домен | зона с доступом к DNS | нужна для сертификатов |

**Про запасной путь.** На этапе `security` доступ по SSH сужается до подсети
VPN. Если к этому моменту нет ни консоли провайдера, ни белого IP, вы
заблокируете сами себя. Проверьте это **до** начала, а не после.

## Шаг 1. Клонировать и осмотреться

```bash
sudo mkdir -p /opt/corp-infra
sudo git clone https://github.com/<org>/corp-infra-bootstrap.git \
     /opt/corp-infra/bootstrap
cd /opt/corp-infra/bootstrap
```

## Шаг 2. Разведка

```bash
./scripts/recon.sh --json | python3 -m json.tool
```

Эта команда **ничего не меняет**: ни файлов, ни пакетов, ни сети. Она читает
`/etc/os-release`, `/proc/meminfo`, `df`, локальные листенеры через `ss` — и
печатает JSON.

Внешние проверки не выполняются никогда: никаких запросов к metadata-сервисам
провайдера, никакого сканирования портов. Оферта adminVPS сканирование прямо
запрещает, и весь репо-сет построен так, что нарушить это невозможно.

Смотреть нужно в раздел `judgments`:

```json
"judgments": {
  "os_tier": "supported",
  "profile_recommended": "core-16",
  "sizing_verdict": "pass",
  "blockers": [],
  "exit_code": 0
}
```

- `blockers` пуст → можно ставить;
- `sizing_verdict: fail` → машина меньше профиля, установка не стартует;
- `sizing_verdict: inconclusive` → проверить не удалось; продолжить можно только
  осознанно, флагом `--force-profile`.

Полное объяснение полей — [`03-state-and-markers.md`](03-state-and-markers.md).

## Шаг 3. Выбрать профиль

```bash
./scripts/sizing-check.sh --static --all
```

Печатает таблицу гейтов G1–G4 по каждому из четырёх профилей, ничего не
устанавливая. Правило выбора простое:

- нужен OpenProject и есть 32 GB → `all-in-one-32`;
- нужны и полноценный CI, и OpenProject, но 32 GB одной машиной не выходит →
  два VPS: `two-vps-split-a` на узле git, `two-vps-split-b` на узле apps;
- во всех остальных случаях → `core-16` (по умолчанию), трекер — GitLab
  issues/boards.

Подробнее — [`02-profiles.md`](02-profiles.md).

## Шаг 4. Запустить установку

```bash
sudo ./scripts/bootstrap.sh --profile core-16
```

Перед этим полезно посмотреть карту этапов — она тоже ничего не меняет:

```bash
sudo ./scripts/bootstrap.sh --check
```

На чистом хосте она покажет пять этапов в состоянии `pending` и завершится с
кодом 0.

## Что произойдёт на каждом этапе

### Этап 1 — `security`

Ставит базлайн: sshd (`PermitRootLogin no`, `PasswordAuthentication no`,
современный набор Kex/Cipher/MAC), ufw с `default deny incoming`, fail2ban,
unattended-upgrades, sysctl, auditd. Генерирует age-ключ и прописывает
publicrecipient в `.sops.yaml`.

**Приватный ключ печатается ровно один раз в терминал и намеренно не попадает в
лог.** Это единственное место во всём наборе, где вывод исключён из
логирования.

### STOP-гейт 1 — escrow age-ключа

Установка останавливается. Нужно:

1. положить приватный ключ минимум в **два независимых места**:
   - общий (не личный) сейф командного менеджера паролей, доступ у ≥ 2 человек;
   - офлайн-копию: запечатанный конверт или распечатка у второго ответственного;
2. выполнить:

```bash
sudo /opt/corp-infra/security/scripts/age-escrow.sh --attest <fingerprint>
```

Скрипт требует **ввести отпечаток руками из escrow-копии**. Совпадение
доказывает, что копия существует и читается, — а не то, что её задокументировали.

Пока `secrets.escrow.ok` не подтверждён, этап `backup` не стартует. Бэкап,
который нельзя расшифровать, бэкапом не является.

### Этап 2 — `vpn-proxy`

Поднимает WireGuard: подсеть `10.8.0.0/24`, порт `51820/udp`, MTU 1420,
`AllowedIPs = 10.8.0.0/24` у клиента (split-tunnel). Выдаёт peer-конфиг
оператора. Затем ставит два Caddy: публичный на `0.0.0.0:443` и внутренний,
привязанный к адресу wg0 — **никогда** к `0.0.0.0`.

Web-UI для WireGuard не ставится ни на каком интерфейсе. Управление пирами —
скриптом `wg-user add/revoke`, конфиги пиров хранятся в git через sops.

### STOP-гейт 2 — переключение на VPN

Установка останавливается. Нужно поднять туннель у себя, убедиться, что
`10.8.0.1` отвечает, и **не закрывать текущую SSH-сессию**, пока новый путь не
подтверждён. Дальше SSH сузится до подсети VPN.

### Этап 3 — `backup`

Инициализирует restic: локальный репозиторий в
`/var/backups/corp-infra/restic-local/` и офсайт по схеме 3-2-1. Ставит
systemd-таймеры с `Persistent=true` и `RandomizedDelaySec`.

Если офсайт-цель не сконфигурирована — **жёсткий отказ, код 1**. Обходного пути
и «тихой деградации до только локального бэкапа» здесь нет намеренно: локальный
репозиторий гибнет вместе с VPS.

### Этап 4 — `ent-infra`

Ставит сервисы по составу профиля. Для каждого — один и тот же шаблон:

1. проверить маркеры `backup.ready` и `proxy.ready` **плюс живой `--check`**
   обеих реп;
2. проверить свободную память: `MemAvailable ≥ steady сервиса + 512 MB`;
3. расшифровать секреты `sops -d` в `/etc/corp-infra/<svc>/.env` с правами 0600;
4. поднять compose — без секции `ports:`, только сети;
5. зарегистрировать vhost в `Caddyfile.d/`, проверить `caddy validate`,
   перезагрузить;
6. опубликовать backup-манифест — единственный способ попасть в бэкап;
7. **negative-check**: убедиться, что сервис НЕ отвечает с публичного адреса;
8. записать маркер.

### Этап 5 — `pop-agents`

Создаёт пользователя `opsagent` — **не** в группе `docker`, — ставит
`/etc/sudoers.d/60-opsagent` из ровно пяти обёрток без единого сырого бинаря,
разворачивает Claude Code CLI, MCP-конфиги и runbooks.

### STOP-гейт 3 — учения по восстановлению

```bash
sudo /opt/corp-infra/backup/scripts/test-restore.sh --scenario vps-loss
```

Установка не считается завершённой, пока восстановление не доказано на практике.
Замеренное время пишется в `/var/lib/corp-infra/backup/drills.jsonl` — заявленный
RTO 4 часа либо подтверждается фактом, либо опровергается.

## Проверка результата

```bash
sudo ./scripts/doctor.sh
```

Запускает все `--check` и печатает сводную таблицу. Ожидаемо: все строки `OK`,
код выхода 0.

```bash
sudo ./scripts/state.sh show
```

Показывает карту этапов и маркеров.

## Если что-то пошло не так

Продолжить с конкретного этапа:

```bash
sudo ./scripts/bootstrap.sh --from backup --profile core-16
```

Прогнать ровно один этап:

```bash
sudo ./scripts/bootstrap.sh --stage ent-infra --profile core-16
```

Логи — в `/var/log/corp-infra/<repo>/<script>.log`. Разбор типичных проблем —
[`04-troubleshooting.md`](04-troubleshooting.md).
