# Траблшутинг

## Сначала — где логи

```
/var/log/corp-infra/<repo>/<script>.log
```

Например: `/var/log/corp-infra/corp-infra-bootstrap/recon.sh.log`.

Каждый скрипт пишет одновременно в файл и на stdout. Формат строки:

```
2026-07-29T10:11:12Z INFO corp-infra-bootstrap/recon.sh: сообщение
```

Единственное исключение из логирования во всём наборе — блок печати приватного
age-ключа в `harden.sh`. Он выводится только в терминал и намеренно не попадает
никуда ещё.

## Что означают коды выхода

Одинаково у всех скриптов всех шести реп:

| Код | Значение | Что делать |
|---|---|---|
| **0** | цель достигнута (мутация применена **или** уже была применена) | ничего |
| **1** | проверяемое условие нарушено. Состояние определено, но плохое | чинить причину |
| **2** | проверить нечем или предусловие не разрешено. Состояние **неизвестно** | выяснить, почему проверка невозможна |

Различие между 1 и 2 существенное. «Sshd не соответствует базлайну» — это 1.
«Не смог прочитать конфиг sshd» — это 2. Второе не должно маскироваться под
первое, а тем более под 0.

## `recon.sh` завершается с кодом 2

**Что это значит.** Либо `MemTotal` меньше `min_ram_mb` выбранного профиля, либо
вердикт sizing получился `inconclusive`.

**Диагностика:**

```bash
./scripts/recon.sh --json | python3 -m json.tool | \
  python3 -c 'import json,sys; d=json.load(sys.stdin); print(json.dumps(d["judgments"], indent=2, ensure_ascii=False))'
```

Смотрите `sizing_verdict` и `blockers[]`.

**`sizing_verdict: fail`** — машина меньше профиля. Флага «продолжить» нет:
это измерение, а не мнение. Варианты — взять профиль поменьше, добавить ресурсов
или разнести на два VPS.

**`sizing_verdict: inconclusive`** — проверить не удалось. Частые причины:

- профиль не найден: проверьте `--profile` и содержимое `profiles/`;
- нет `python3`: он нужен для чтения JSON. `apt-get install -y python3`;
- `/proc/meminfo` или `df` недоступны в этой среде (контейнер с урезанными
  правами).

Продолжить осознанно:

```bash
sudo ./scripts/bootstrap.sh --profile core-16 --force-profile
```

Факт запишется в `state.json` как `profile_forced: true`.

## `sizing-check` показывает FAIL

Смотрите, какой именно гейт:

| Гейт | Что не так | Выход |
|---|---|---|
| **G1** | суммарный steady больше 75 % RAM | профиль поменьше или больше RAM |
| **G2** | суммарный cap больше 110 % RAM | то же; выше 110 % OOM реален |
| **G3** | overcommit есть, а `contention_policy` в профиле не объявлен | ошибка в самом профиле: добавьте `"contention_policy": "slices-v1"` и блок `slices` |
| **G4** | диска меньше, чем `Σ disk × 1.15` | добавить диск. Именно 15 % запаса — это место под рост репозиториев и снапшоты |

Пересчитать без хоста:

```bash
./scripts/sizing-check.sh --static --all
```

Если провалился гейт на **штатном** профиле — это баг профиля, а не хоста, и
чинится правкой `profiles/*.json`. Гейт G-07 в CI ловит такое до установки.

## Docker не ставится

**Диагностика:**

```bash
sudo ./scripts/ensure-docker.sh --check
```

| Симптом | Причина | Решение |
|---|---|---|
| `unsupported OS family`, код 2 | ОС не из apt- или dnf-семейства | поставить Docker вручную, затем `--check` |
| падает на `apt-get update` | нет сети или DNS | проверить egress; репозиторий Docker берётся по HTTPS |
| ключ не скачивается | исходящий 443 закрыт | см. ограничения провайдера в [`../providers/README.md`](../providers/README.md) |
| `docker compose` не найден | стоит старый `docker-compose` v1 | нужен плагин `docker-compose-plugin`; v1 не поддерживается |
| `daemon.json` не совпадает | файл правили руками | скрипт делает резервную копию и приводит к целевому виду; проверьте `default-address-pools` и ротацию логов |

Скрипт **намеренно не использует `get.docker.com`**: тот скрипт написан на `sh`
с `set -e` без trap, без retry и без идемпотентности — то есть ровно с теми
свойствами, от которых защищают конвенции этого набора.

Пул адресов `172.28.0.0/16` с размером подсети 24 задаётся явно, чтобы Docker не
конфликтовал с VPN-подсетью `10.8.0.0/24` и корпоративными сетями.

## Этап «зациклился» или падает при повторе

Все скрипты идемпотентны, но идемпотентность построена на **проверке
реальности**, а не на маркерах: перед каждой мутацией скрипт смотрит, сделана ли
она уже (`command -v`, `systemctl is-active`, `docker inspect`, `grep -q`).

Поэтому повторный запуск на настроенной системе безопасен. Если этап всё-таки
падает раз за разом:

1. Запустите проверку самого этапа и прочитайте вывод:

   ```bash
   sudo /opt/corp-infra/<repo>/scripts/<entry>.sh --check
   ```

2. Посмотрите последние строки лога:

   ```bash
   sudo tail -50 /var/log/corp-infra/corp-infra-<repo>/<entry>.log
   ```

3. Почините причину и перезапустите **только этот этап**:

   ```bash
   sudo ./scripts/bootstrap.sh --stage <name> --profile core-16
   ```

Если падение происходит на предусловии (`stage '<x>' marker is ok but live check
failed`), проблема не в текущем этапе, а в предыдущем. Читайте раздел про DRIFT
в [`03-state-and-markers.md`](03-state-and-markers.md).

---

## `bootstrap.sh --check` показывает DRIFT

Маркер и реальность не согласуются. Полный разбор — в
[`03-state-and-markers.md`](03-state-and-markers.md), краткая версия:

- маркер `ok`, живая проверка `fail` → **чините реальность, не маркер**;
- маркера нет, живая проверка `ok` → перезапустите этап, он допишет маркер;
- `host_id` не совпадает → каталог состояния приехал с другого хоста; маркеры
  чужой машины не принимаются намеренно.

## «Я заблокировал себе SSH»

Этап `security` сужает доступ по SSH до подсети VPN. Если запасного пути не
было, остаётся:

1. **консоль провайдера** (KVM/VNC в панели) — штатный путь;
2. **whitelisted IP администратора**, если он был прописан заранее.

Именно поэтому наличие break-glass фиксируется в `state.json` и проверяется в
`harden.sh --check` **до** сужения доступа. Если проверка выдала предупреждение
про break-glass, а вы продолжили, — это тот самый случай, о котором она
предупреждала.

Профилактика: не закрывайте текущую SSH-сессию на STOP-гейте 2, пока не
убедились, что путь через VPN работает.

## Расхождение версий библиотеки

```bash
./scripts/sync-lib.sh --check
```

| Вывод | Что значит | Решение |
|---|---|---|
| `VERSION-DRIFT` | у репы другой `lib/VERSION` | обновить репу до совместимой версии из `versions.env` |
| `CONTENT-DRIFT` | версии равны, а содержимое `common.sh` разное | кто-то правил вендоренную копию. Это запрещено |
| `MISSING` | репы или файла нет | репа ещё не склонирована — нормально до первого запуска |

Восстановить каноникал во всех репах:

```bash
sudo ./scripts/sync-lib.sh --yes
```

Нужна новая функция в библиотеке — это правка **каноникала** `lib/common.sh` в
этой репе, плюс подъём `lib/VERSION`, плюс `sync-lib.sh --yes`. Локальная правка
вендоренной копии не переживёт первую же синхронизацию и будет поймана гейтом.

## Общая проверка «что вообще происходит»

```bash
sudo ./scripts/doctor.sh
```

Запускает `recon.sh --check`, `sizing-check.sh --check`, `sync-lib.sh --check` и
`bootstrap.sh --check`, печатает сводную таблицу. Ничего не меняет.

Код выхода агрегируется по правилу «fail важнее, чем inconclusive»: 1, если хоть
что-то провалено; иначе 2, если хоть что-то не удалось проверить; иначе 0.

## Куда сообщать, если ничего не помогло

Соберите:

```bash
./scripts/recon.sh --json > /tmp/recon.json
sudo ./scripts/state.sh show > /tmp/state.txt
sudo ./scripts/doctor.sh > /tmp/doctor.txt 2>&1
sudo tail -200 /var/log/corp-infra/*/*.log > /tmp/logs.txt
```

**Перед отправкой просмотрите файлы глазами.** В логах не должно быть секретов
по построению, но проверить дешевле, чем потом ротировать ключи.
